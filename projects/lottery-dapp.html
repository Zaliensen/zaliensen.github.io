Lottery DApp — owner and participant workflows

A bootcamp DApp presents two views of one contract workflow: the owner controls betting windows, while participants acquire tokens, enter, inspect the prize pool and withdraw eligible balances. Its portfolio value is the connection among user actions, contract state and separate fee/prize accounting.

Source behavior

backend/contracts/Lottery.sol creates a payment token, opens/closes betting, records bet slots, chooses a winner, tracks prize and owner pools, and supports token purchase/return and withdrawals. LotteryToken.sol supplies ERC20 role-based mint/burn behavior. The Next.js/React UI offers wallet, owner and participant panels. The source explicitly credits Matheus Pagani and labels the lottery teaching-only.

What was prepared

This package uses the substantive code that matches the repository's master branch; its default main branch is only a placeholder. Eighteen of nineteen relevant remote source/interface/style files matched the local family after line-ending normalization. Only ABI interfaces are retained from generated JSON. Deployment scripts/package commands, credentials, dependencies and image logos are excluded; the navbar uses text.

The missing OpenZeppelin direct dependency was declared using a compatible recovered version; the frontend now explicitly declares ethers5.7.2. A new JavaScript Hardhat configuration selects a local network only and Solidity0.8.18.

Setup and checks

Recovered tooling is Hardhat2.10-era/toolbox1, OpenZeppelin4.x, Next13.1.2, React18.2 and wagmi0.12. No exact clean dependency lock was recovered for the assembled package. Backend and frontend have separate manifests. Provision and review legacy dependencies before any isolated local build; generated dependencies are not included.

Offline Solidity0.8.18 compilation with installed OpenZeppelin4.9.1 passed. JS/JSX syntax and relative imports passed static checks. No browser flow, Hardhat test suite or transaction was executed. No dedicated original lottery tests are claimed in this package.

Limitations and next steps

The teaching contract uses block randomness with an explicitly documented weak randomness model. Token conversion can round; token approvals, closing-window boundaries, empty rounds, fee/prize separation and withdrawals need adversarial tests. Changing those rules would be a new design decision, so the cleanup preserves them and records the limits. This is not represented as suitable for real-money operation.
