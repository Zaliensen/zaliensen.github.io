Voting DApp — wallet interface and token API recovery

A recovered interface experiment connects a browser wallet to voting-token and ballot operations. It separates what a participant sees from the server's contract access and illustrates the work needed to keep UI, API and blockchain interfaces consistent.

Workflow and architecture

The Next.js/React frontend displays wallet balance, requests tokens using a signed message, lists proposals and submits votes through ethers. The NestJS backend exposes token/ballot addresses, balances, supply, receipts, proposals and past-vote reads. Its token-request route validates a signature and then uses a configured server signer to mint.

The backend vote method only returns the supplied signature/hash. It does not cast a vote: the frontend performs the contract transaction. ABI-only JSON files are retained as interface definitions; generated bytecode is removed.

Recovery reconstruction and touchups

The current local component had become a small lottery scaffold. This review package reinstates the longer voting component recovered from VS Code history, pairs it with the retained frontend shell/backend, and supplies the backend manifest/config from a sibling project copy. This assembled combination is explicitly a recovery reconstruction, not an unchanged release.

The undefined vote-display setter was corrected to setVotesData; failed requests now clear loading. Controller tests were aligned with existing methods/response shapes and use mocked service calls. No new endpoint or blockchain behavior was invented.

Setup and validation

The recovered frontend uses Next13.1.2, React18.2, wagmi0.12 and RainbowKit0.12; the backend uses Nest9, ethers5.7.2 and TypeScript4-era dependencies. The source syntax was checked with installed TypeScript5.0.4. Minimum Node versions and a single reproducible lock for the assembled package are not established. The ethers direct dependency is now explicit in the frontend manifest.

Frontend and backend are separate package roots. Blank .env.example files enumerate configuration names. Browser NEXT_PUBLIC_ values are public; a minting private key belongs only on a server. No real values are included. A future local setup would provision compatible dependencies, configure disposable test contracts, run backend tests, and then review UI/API behavior. No service was started and no wallet connected during preparation.

Remaining blockers

The recovered vote-balance UI requests /api/vote, while the retained server exposes /past-votes/:address/:voteIndex; the desired snapshot/block input is unresolved. Signed mint requests use a fixed message without a documented nonce/replay policy. Wallet availability, errors and ABI/version compatibility require integration tests. Existing limitations mean this is not a working end-to-end demo or production voting service.

Team and source context
