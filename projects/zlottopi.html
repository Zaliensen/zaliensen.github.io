ZLottoPi — transaction intake, rounds and payout workflow

Publication scope

This is a documentation-only portfolio entry. The source package, configuration files and any local commands described below refer to privately reviewed material; that package is not currently distributed from this page. The notes describe the prototype and its limits, not a publicly reproducible deployment.

A recovered Rust prototype that connects Zcash wallet observations to a small lottery workflow. Its useful engineering story is how incoming transactions become bet records, round decisions and retryable payout work. This is source for technical review, not a running or audited financial service.

Workflow and architecture

watcher.rs reads Zingo CLI output and records transactions in SQLite. bet_processor.rs interprets incoming activity; bet_lanes.rs and econ.rs define bet categories and arithmetic. round_manager.rs creates and closes rounds using seed commitments. payout_processor.rs prepares/processes payouts, including orphaned bets and retry paths. db.rs and migrations/ expose the state model. payment_uri.rs and qr_generator.rs support payment instructions. encryption.rs provides AES-GCM seed encryption with Argon2 derivation.

zingo.rs is the external-system boundary: it launches a Zingo CLI process, parses mixed text/JSON output and issues wallet commands. main.rs orchestrates those components. This separation is useful for discussing integration assumptions, operational failure handling and where an adapter needs stronger contracts.

What this package changes

The operational configuration, wallet state, databases, logs and archives are excluded. config.example.toml uses local/disposable placeholders. A hardcoded seed passphrase was removed from the staged code; ZLOTTOPI_SEED_PASSPHRASE is required before database initialization. The example environment file is documentation: this Rust code reads the process environment and does not load dotenv automatically. Original files remain untouched.

Setup and review

The recovered package uses Rust edition 2021, Tokio1, SQLx0.7/SQLite, Axum0.7, image0.25 and the versions in Cargo.lock. No original minimum Rust toolchain version was recorded; edition2021 alone does not establish that minimum. Zingo CLI is an external dependency and is not bundled.

Start by reading src/main.rs, src/db.rs and the adapter. For a future isolated build, provision the locked dependencies, then use cargo check --locked --offline and cargo test --locked --offline. Those commands were not run during preparation. Do not use cargo run as a harmless preview: the default path can synchronize wallets, change state, close rounds and send payouts. Even the command labeled test-payout initializes state before dispatch. No live-run recipe or wallet credentials are included.

Evidence and limitations

All 13 Rust modules passed installed rustfmt syntax parsing. TOML/lockfile structure and package exclusions were checked. Six original encryption/payment-URI test functions remain, but were not executed. Syntax parsing is not Rust type checking, integration testing or evidence that wallet commands succeed.

Review priorities include idempotent payout confirmation, failure recovery around database/file updates, locking across asynchronous process calls, encryption-key lifecycle, seed auditability and reliance on external CLI output. No transaction totals, users, operational reliability or production security claims are supported by this recovery. The code still contains actual transfer paths.
