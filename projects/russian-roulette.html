Russian Roulette — shared smart-contract game prototype

A bootcamp final project connects an elimination-game state machine to a wallet interface. Participants join, rounds eliminate players, a winner becomes eligible to withdraw the prize, and the owner has a separately tracked fee balance. This package makes those rules and their test assumptions reviewable.

Architecture and behavior

backend/contracts/RussianRoulette.sol stores players, round timing, game status, a winner and owner fees. Each entry requires 0.1 ETH, adds 0.01 ETH to the owner pool and automatically starts the game at eight entries; manual start requires at least two. A previous block hash selects an elimination index after a three-block interval. The Next.js/React frontend calls contract methods through ethers and a connected wallet.

backend/test/RussianRoulette.ts now tests initial state, the actual entry amount, fee accounting, rejection of the stale amount, eight-player automatic start and the minimum manual-start condition. backend/scripts/deployR.ts remains a historical deployment example, not an automatic setup step.

Cleanup and test alignment

The staged contract capitalization now matches its factory name. The recovered tests expected four players and 0.05 ETH; their assertions were replaced with the actual contract rules. The original contract's economics and elimination design were not changed. An old Hardhat configuration contained a private-key literal: it was excluded, and a new local-only configuration contains no accounts or external network targets. No original secret value is retained here.

Setup and verification

The backend manifest records Yarn3.6, Hardhat2, ethers5, TypeScript and OpenZeppelin4.9-era dependencies. The UI uses Next13.1.2/React18.2/wagmi0.12. Frontend/backend have separate package roots. No complete reproducible lock or original Node minimum was established. Ethers is now an explicit frontend dependency.

Offline solc0.8.18 compilation passed and JS/TS/JSX syntax checks passed. The updated test suite has not been executed. After provisioning compatible dependencies in an isolated environment, the intended backend command is yarn hardhat test --network hardhat. Do not run the historical deployment script as a preview; it uses a configured provider and signer. No wallet connection, live deployment or browser demo was performed.

Remaining design risks

The duplicate-entry check inspects the next player slot rather than all existing entries, so it does not establish unique participation. The block-hash randomness is manipulable. Restart/reset behavior and withdrawal/round edge cases need specification and testing. These are substantive design issues, not formatting defects, and were not silently changed in a portfolio cleanup. This is not a secure gambling product.
