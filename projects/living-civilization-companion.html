Living Civilization Companion

Publication scope

This is a documentation-only portfolio entry. The source package, configuration files and any local commands described below refer to privately reviewed material; that package is not currently distributed from this page. The notes describe the prototype and its limits, not a publicly reproducible deployment.

A Python prototype for turning game observations into a persistent campaign narrative. Its recovered architecture separates screen capture, event interpretation, campaign memory, narrative selection, voice and a desktop interface.

This package is a secondary engineering case study. The verified entry point is a deterministic offline walkthrough of the event/memory core. The full capture, microphone, model-service and GUI integrations have not been validated in this preparation.

Run the offline walkthrough

Historical local setup notes for the unpublished review package (not a runnable website command):

python demo.py
python -m unittest discover -s tests -p test_offline_core.py -v

Both commands use the standard library only and require no installation or credentials. The walkthrough constructs a synthetic Printing event, merges it into temporary SQLite memory, selects newspaper narration, applies a correction, closes/reopens the database and prints the result. The temporary directory is removed when it finishes. It does not import capture, GUI, microphone or external client modules and does not load an environment file.

Design choices worth discussing

intelligence/event_schema.py provides a structured event boundary. event_merger.py updates world facts and media unlocks. world/campaign_memory.py stores events, protected facts, corrections, story threads and estimated costs in SQLite. narration/director.py chooses narration based on event importance, quiet mode and available media. world/cost_control.py checks projected daily spending and hourly screenshot counts before a proposed vision call.

The core makes uncertainty and operational limits visible: observations have confidence and importance, users can correct memory, and cost checks precede some external work. These are design mechanisms, not proof that screenshots are interpreted correctly or that all external spend is constrained. Cost values are estimates, and the guard is not a billing reconciliation system.

Staged changes and contents

The private review package contains recovered Python modules, prompts, requirements and tests. Original .env, databases, screenshots, audio, installed packages and launch scripts that install/start software are excluded. A blank environment example was prepared privately for later review.

Staged defaults are mock mode on, automatic start off and spoken narration off. Existing persisted settings can override defaults in the full app; this walkthrough bypasses that loading path. The new demo.py and tests/test_offline_core.py are portfolio-preparation additions. SOURCE_MANIFEST.json retains original hashes and records the changed config separately. Originals were preserved.

The optional full application requires packages listed in requirements.txt, including PySide6, capture/audio libraries and the model SDK. pyproject.toml does not enumerate those dependencies. No dependency installation was performed. Do not infer full readiness from the offline test; supported API/model names, Windows capture permissions and audio behavior require a separate integration review.

Evidence, validation and next work

Recovery candidate C003 came from a local Codex conversation workspace dated July 21, 2026 and a matching output archive. No independent repository history was established. Treat it as an AI-assisted prototype and verify the author's specific contribution before making ownership claims.

Three standard-library tests passed: event unlock/correction/persistence; projected budget and hourly-limit boundaries; and mock/manual/silent staged defaults. The original broader smoke test and the full desktop loop were not run. VALIDATION.md records this boundary.

The next useful step is a fixture-driven event evaluation with known expected outcomes, followed by a mock desktop walkthrough. Add validation of settings, confidence thresholds and failure recovery before any live capture or model service. A portfolio discussion can focus on event-to-action workflow, state correction and operational constraints, without claiming production deployment or user outcomes.
