Tokenized Ballot — token permissions and voting snapshots

Publication scope

This is a documentation-only portfolio entry. The source package, configuration files and any local commands described below refer to privately reviewed material; that package is not currently distributed from this page. The notes describe the prototype and its limits, not a publicly reproducible deployment.

A shared bootcamp experiment connecting an ERC20 voting token to weighted proposal voting. It is useful for examining how permissions, historical data and workflow rules must agree across contracts and tests.

Behavior and structure

MyERC20Votes.sol extends OpenZeppelin ERC20Votes/AccessControl, grants minting roles and delegates newly minted/transferred tokens. BalletTokenized.sol defines the Ballot contract: named proposals, historical voting-power checks, current-balance checks, a one-vote flag and result selection. tests/TokenizedBallot.ts and the deployment example document the intended integration.

The staged transfer test now mints tokens within its own fresh fixture before transferring. No token economics or voting rules were changed. The source filename BalletTokenized.sol is retained for provenance even though the contract is named Ballot.

Setup and verification

Recovered versions target Hardhat2.14, ethers5, TypeScript, Yarn3.5.1 and OpenZeppelin4.8.3-compatible APIs. Solidity0.8.18 is selected by a new local-only configuration. The actual offline compilation check used installed OpenZeppelin4.9.1 and solc0.8.18 and passed; that is not a full lockfile reconstruction. Dotenv is declared directly for the retained script. No dependency install occurred.

For a future isolated test after provisioning compatible dependencies: yarn hardhat test --network hardhat. Generated TypeChain bindings are intentionally absent until compilation. The test suite was not executed during preparation; TypeScript syntax and relative imports were checked.

Known design ambiguity

targetBlockNumber is used both as a historical block identifier and as a number of seconds added to block.timestamp. These are different units and the constructor currently conflates them. Voting tests are partly commented out. The cleanup deliberately does not invent a new governance model to hide this ambiguity. A next revision should specify snapshot semantics and voting duration separately, then test mint/transfer/delegation and block-boundary behavior.

The contract is not presented as a deployable election or governance system. No on-chain activity, performance, user adoption or security outcome was verified.
