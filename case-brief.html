Designing evidence a teacher can interpret

Zachary Halaby — creator and classroom workflow designer. Developed and iterated with AI coding assistance.

A teacher needs to decide what to teach or support next. A single “correct” score is insufficient when it hides an initial mistake, a retry, an answer cue or an unobserved response. I designed the evidence workflows in Mother Hen and Jungle Book to keep those distinctions visible. This public demonstration isolates the shared rules using invented scenarios.

Start with the decision

The immediate user is a teacher reviewing an activity. The design question is: What happened on the first response, under which task conditions, and with what support? That information can inform a teacher's next step. The demonstration itself does not diagnose, recommend placement or measure mastery.

Workflow concern Design choice Why it matters
A retry ends successfully Retain initial and eventual outcomes separately Later success does not overwrite the original observation.
A learner needs a way to activate a response Distinguish access support from an answer cue Access alone is not treated as evidence that an answer was supplied.
Support was not confirmed Keep the observation unknown Missing confirmation cannot silently become “independent.”
A session is interrupted Exclude it from the comparison An incomplete observation is not an incorrect response.
Choice count or response method changes Separate task-condition groups A changed task does not silently become a like-for-like comparison.

Follow the workflow

Task conditions → first response → support history → later response → explicit interpretation → teacher review. The public interface lets a reviewer change the scenario and see which interpretation changes. It holds invented examples only in memory; it accepts no learner records.

The implementation retains six functions and four initializers from the related applications. A new adapter adds guards for missing initial outcomes, unknown prompt codes, legacy versions and interruptions. The technical notes explain the exact retained code and provenance.

Three decisions to inspect

  1. Choose Correct after retry. Explain why eventual correctness does not erase the first response.
  2. Compare AAC access only with Prompted success. Explain the difference between making an input accessible and revealing an answer.
  3. Remove adult confirmation or change the number of choices. Explain why the result becomes unknown or belongs to a different comparison group.

Tradeoffs and limits

Explicit support confirmation adds work for the adult; inferring “no help” would create cleaner-looking but less trustworthy records. Separating task conditions also makes comparisons less convenient. The grouping signature is a prototype aid: it cannot establish that two assessments are educationally equivalent.

The public version omits the full lesson experience and original reporting integrations so the decision rules can be inspected in isolation. It does not demonstrate a production data pipeline, multi-user permissions, durable audit logging or Palantir platform integration.

Evidence available now

Seven Node checks cover the selected evidence rules and edge cases. Nine browser checks cover representative paths, keyboard operation, narrow layout and the absence of persistence or external requests. The repository records their scope. These checks establish behavior in the reviewed demonstration; they do not establish learning gains, real adoption or compatibility with every assistive device.

How I would evaluate a rollout

This is a proposed next step, not a completed pilot. First, agree with teaching staff on the meaning of each field and the decision the observation supports. Use invented examples to train reviewers, including an unobserved response and a supported success. Ask each reviewer to explain the result without coaching; record confusing labels and unnecessary steps.

For an institutionally authorized pilot, define access, retention, review and correction procedures before introducing real data. Evaluate interpretation agreement, missing-confirmation frequency, workflow completion and time needed to record an observation. Keep those usability measures separate from any independently designed evaluation of learning. Review feedback, change one rule or interaction at a time, and repeat the same checks before expanding use.

A contrasting workflow

World Food Truck shows a different design problem: guiding a participant through choices, planning, decoration, review and delivery. Its public version includes keyboard controls and protects against duplicate actions and stale delayed transitions. Together, the projects show both the meaning of an observation and the sequence needed to complete a task.
